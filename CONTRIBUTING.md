# Maintaining the public record

[Project index](README.md) · [Publication policy](PUBLICATION.md)

## Begin with the reader

State the problem, the intended user, and the responsibility being examined. Use the actual project behavior rather than a generic feature list.

A project overview should let a reader understand what the project does and choose whether to examine the detailed case study. The case study should explain the workflow, architecture, tradeoffs, and limits without repeating the overview sentence by sentence.

## Support the claim

Distinguish an implemented responsibility from a proposed improvement. A review question is not evidence that a test has passed. The existence of a connection module is not evidence of a working live integration.

Preserve team attribution and describe AI assistance honestly. Never invent results, usage, historical activity, testimonials, or completed features.

## Publish only the intended material

Keep source, records, configurations, attachments, screenshots, and development history private. Review every public file against the publication policy before committing it.

Architecture diagrams should explain a real relationship. Use descriptive labels, include a plain-language explanation, and avoid decoration that adds no information.

## Finish the review

- Read the overview as a new visitor and check that the main point appears early.
- Check that case-study links, section links, and the project index agree.
- Confirm that diagrams render and their surrounding text explains the same workflow.
- Remove unsupported claims and unnecessary repetition.
- Check the full proposed publication for prices, numeric content, emails, contacts, credentials, and personal records.
- Verify that private repositories and histories remain private.

Make a coherent update with a truthful description of what changed. Publication checks establish the state of the public documents, rather than a security or performance guarantee for the underlying applications.
